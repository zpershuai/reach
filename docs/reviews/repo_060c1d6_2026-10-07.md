# 项目整体架构文档

## 1. 项目定位与目标

把 Agent / MCP 客户端接到设备工作区：读改文件、在显式启用后跑可信 Node 脚本。Gateway 不执行工作区；Engine 不出入站端口，只出站心跳并按需建立会话。

## 2. 仓库整体结构总览

```
crates/reach-rpc/                 Rust Engine、协议 DTO（fs.*）、Runtime、Tools、Process
packages/reach-rpc/               Gateway、共享 MCP 核心、TS 协议 DTO
packages/grok-bot-mcp-connector/  stdio 发行壳（re-export + copy-mcp-core）
grok-bot-plugin/                  HTTP MCP 插件模板
openspec/specs/                   当前契约
docs/deploy/                      公开部署文档
scripts/                          verify / 安装 / Node runtime
```

体量（源文件行数，约）：`workspace.rs` 2148、`runtime.rs` 1444、`gateway.ts` 927、`process.rs` 834、`lib.rs` 659、`gateway.test.ts` 1726。

## 3. 系统核心执行流程

```
Agent / MCP
    │  stdio 或 HTTPS /mcp
    ▼
Gateway (TS)
    │  heartbeat + 一次性 session token + WSS
    ▼
Engine Runtime (Rust)
    └── SessionDispatcher → Tool → WorkspaceFilesystem / ProcessManager
```

1. `engine.rs` 解析 `EngineConfig`，装 `default_registry()`，跑 `EngineRuntime::run()`。
2. 状态机：`Boot → Heartbeating → Waiting → Connecting → ActiveSession → Draining → Heartbeating | Backoff`。
3. 会话内：控制车道在 Runtime 线程（`execution.rs`），Tool 在串行 worker。
4. Dispatcher：绑 session → requestId 去重 → 取消 → deadline → `tool.call` 规范化 → 授权 → Tool。
5. Gateway `executeRpc` 被 REST `/session/rpc` 与 in-process MCP 共用。stdio MCP 多一跳 HTTP。

## 4. 顶层模块划分

见下一章评估矩阵。分层上：契约（两端 DTO）→ Gateway 控制面 → Engine Runtime → Dispatch → Tools → Workspace / Process。

## 5. 模块依赖关系与调用链

`createGateway()` 先切 `/mcp`，再按 `engineId` 进隔离的 `createEngineGateway`。HTTP MCP 经 `EngineApi` 打同一套会话状态机。stdio 经 `HttpGatewayClient` 走 REST。Engine 只依赖传输 trait 与时钟，测试注入 Fake。

## 6. 数据流 / 控制流

- 控制面：`session.ready | renew | close | closed`，与 data-plane envelope 分离。
- 数据面：`reach-rpc/1.0` request/response/error；写与 process.run/stop 必须带 Gateway 签发的 grant。
- 遗留：`session.complete` / `job.done` 仍翻译成关闭，不是成功主路径。

## 7. 关键设计决策

- 控制面与执行面分离（Model B）。
- Engine 把超时当硬上限，Gateway/Agent 不能放宽。
- 授权两道：Gateway 验 scope/expiry，Engine 验 claim 形态 + 本地 process 白名单。Engine **不**再验 path scope。
- 取消合作式；已过 commit 边界的写成功不被改写成失败。
- process 默认关闭；workspace 校验不是沙箱。
- MCP HTTP 静态下划线工具 + 非阻塞冷启动；stdio 动态点号工具保留。

## 8. 配置、构建、部署与运行机制

组件版本：Engine `0.2.0`，Gateway/MCP `0.3.0`。验证入口 `bash scripts/verify.sh`。部署文档在 `docs/deploy/`。私有主机/凭证只在 `.reach/`。

## 9. 测试与质量保障现状

Rust 侧约 100+ `#[test]`，Fake transport/clock 可单步 Runtime。TS 侧 `gateway.test.ts` / `mcp.test.ts` / connector 集成测真实 Engine。主路径锁得住；缺口见后文。

## 10. 整体优点、风险与演进方向

优点：安全边界、状态机、契约测试、process 产品边界克制。风险：上帝文件、process 未入共享契约、文档总览滞后、MCP 继承错位。演进应沿现有缝切分并对齐文档/spec，而不是换框架。

# 设计框架与设计模式

## 已经在用、且用对了的

| 模式 | 证据 | 评价 |
| --- | --- | --- |
| Ports & Adapters | `HeartbeatTransport` / `SessionTransport` / `Clock`（`crates/reach-rpc/src/runtime/transports.rs`） | 整仓骨架 |
| 显式状态机 | `RuntimeState` + `step()` 单步推进（`runtime/state.rs`、`runtime.rs`） | 比再引入 State 类层次更好 |
| Registry + Strategy | `Tool` + `ToolRegistry` + `AccessClass` | 加 Tool 不改传输 |
| Pipeline / Middleware | `SessionDispatcher::dispatch` 固定顺序 | 安全边界，不要做成可插拔链 |
| Adapter | 单层 `tool.call` 在授权前展开 | 防 grant 绕过 |
| Policy Object | `TimeoutPolicy`、`ProcessPolicy` | Engine 硬上限 |
| Discriminated Union | process grant `kind: execute \| control` | 与写 grant 互斥 |
| RAII | `SessionContext` Drop 关游标并 drain 进程；HTTP MCP `reading` pin | |
| Facade | `createGateway`、`EngineRuntime::run` | |
| GatewayClient Adapter | `HttpGatewayClient` / `InProcessGatewayClient` | HTTP MCP 与 stdio 出站端口 |

## 要不要再上“多种设计模式”？

**不要。** 再加 Abstract Factory、Visitor、Observer 总线、Decorator 栈、DI 容器、Actor、async runtime，会与现有同步 + `thread::scope` + Fake 测试模型冲突。

该做的是让后加能力服从现有框架：

| 建议 | 解决什么 | 落点 | 不要做成 |
| --- | --- | --- | --- |
| process DTO 收进共享契约 | 两端第二套 schema，drift 风险 | `lib.rs` / `index.ts` + fixtures | 不要上 schema 生成器 |
| 按 Engine 的缝拆 Gateway | 927 行闭包 | `EngineSessionState` + `SessionRpcForwarder` + 薄 HTTP | 不要上 Nest |
| MCP 组合代替继承 | `RemoteMcpServer extends McpServer` 后几乎全覆盖 | `McpProtocol` + `GrantAwareInvoker` + 两套所有权表 | 不要加深继承 |
| 拆 `workspace.rs` / `process.rs` | 单体难审 | 内部模块，对外仍 Facade | 不要虚幻 Filesystem trait / 热加载插件 |
| 统一 Cancellation 小类型 | bool + AtomicBool 双轨 | `cancel::{Flag,Token}` | 不要引入 async cancel 生态 |
| 轻量 `FnTool` | 7 个 fs_* 样板 | 泛型适配，不是插件 | |
| HTTP MCP 显式生命周期 | `handle()` 仍是长过程 | `uninitialized / active / retiring` | 不要事件总线 |

`ExecutionPolicy` 目前只有 `Serial`，在真正要只读并发之前不要提前实现策略层次。Dispatch 管道是固定安全边界，做成可插拔 middleware **反而危险**。

# 代码质量评估

### 1. 正确性

- 评分: 8/10
- 会话租约、去重、deadline、grant、ready 门闩、process launchId、MCP 所有权主路径有测试锁住。
- 当前树上仍可能误导或在边角出错的：
  1. HTTP MCP `releaseReadPin()` 在 `enqueue` 之前，极短窗口 `reading===0 && queued===0` 可能撞 idle retire；随后 `requireActive` 404，**不会**再打开无人认领 Engine（10-07 高危已修，残留窗口小）。
  2. `session_close` 在无 session 时幂等成功，可能让模型以为“我关掉了”；他人持有已返回 `ENGINE_BUSY`。
  3. `/mcp` 与 `/session/rpc` 的 64KiB 不对称是有意的：MCP 近上限可过，REST 仍可能 413。
  4. HTTP 408 不取消已 enqueue 的 mutation（契约：先 re-read）。客户端不遵守会双写。
  5. `fs.grep` 是 `line.contains` 子串，不是正则；gitignore 无 `!` 否定。若文档/模型当正则用会错。
  6. `SESSION_NOT_READY` 导出但 dispatcher 未使用。

先前审查已修、不再当活问题：MCP `readBody` 期间不 pin 导致孤儿 Engine；`session_close` 误关他人；spawn 失败后再跑同一 launchId 变成成功响应（现对 `RUNTIME_UNAVAILABLE` 持续返回该错误）；Execute 失败被改写成 `DEADLINE_EXCEEDED`（dispatcher 对 Execute 保留原码）。

### 2. 安全性

- 评分: 8.5/10
- Unix no-follow / FIFO 非阻塞拒绝 / 非普通文件 fail-closed；明文 Gateway 仅 loopback；远程 TLS + token；`timingSafeEqual`；Origin 默认拒绝带该头的请求；process 默认空白名单、`env_clear()`、不继承 `NODE_OPTIONS`、argv 在 `--` 之后。
- 产品声明而非漏洞：脚本等于 Engine 账号权限；Engine 不复验 grant path scope；`REACH_MCP_ALLOWED_ORIGINS` 对浏览器/webview 是必配。不要改成通配符。
- process 注释诚实：`Workspace validation is not a sandbox.`

### 3. 性能

- 评分: 8/10
- in-process `EngineApi` 避免 loopback HTTP。冷启动不占用 25s 去等 120s 心跳。队列、事件缓冲、request-id、日志字节均有上限。
- 扣分：`process.run` 入口读取仍在串行 dispatch 上（最大 8MiB），会挡住同 session 的 status/stop。`parse_params` 把 JSON `Value` 先序列化再解析。每个任务多条监督线程，默认并发 4 可接受。

### 4. 可维护性

- 评分: 6.5/10
- OpenSpec 驱动、Fake 可测 Runtime、`executeRpc` 共用，方向对。
- 扣分重：`workspace.rs` / `runtime.rs` / `gateway.ts` / `process.rs` 体量集中；process DTO 未入契约层；`copy-mcp-core.mjs` 无构建断言；`RemoteMcpServer` 继承错位；双 `initialized`；crate 级 `session` 与 `runtime::session` 同名不同层。

# 改进分析

### Architecture problems

- Gateway 未按 Engine 已选分层切开。涉及 `gateway.ts`。方向：显式 session 状态对象，而不是换框架。
- process 未进入共享契约层。涉及 `lib.rs`、`index.ts`、`process.rs`、`process.ts`。

### Interface or abstraction problems

- MCP 继承错位、双 initialized。涉及 `remote-server.ts`、`server.ts`、`http.ts`。
- 授权 Read/Write 与 Execute/Control 分裂。涉及 `authorizer.rs`、`tool.rs`。
- 取消双轨。涉及 `session.rs`、`workspace.rs`、`dispatcher.rs`、`execution.rs`。

### Reliability or correctness risks

- 心跳 env 文档归属错误（运维风险）。
- MCP/REST 64KiB 不对称、408 不取消 mutation：有意语义，需文档/客户端遵守。
- grep 子串 vs 正则预期。

### Performance risks

- 串行 dispatch 上读 8MiB 入口。有界，不是热路径灾难。

### Maintainability and readability gaps

- 四个上帝文件；fs Tool 样板；错误码过于扁平（几乎全是字符串 code）。

### Testing and observability gaps

- Authorizer Execute/Control 单测薄。
- 无 `copy-mcp-core` 契约测试。
- process 无跨语言 fixture。
- `default_registry` 测试不断言 Unix process 方法。
- 错误同质化导致测试只 assert code 字符串。

### Documentation debt

- 见 D1–D13。优先根 README 心跳归属、OpenSpec 工具列表、plugin skills、关闭原因 `shutdown`。

# 项目学习 / 重写路线图

## 1. 学习目标与前置知识

目标：能独立讲清一次 `fs.read` 和一次 `process.run` 如何从 MCP 走到 Engine 再回来，以及 grant / lease / drain 各卡在哪。前置：Rust 同步 I/O、TypeScript HTTP、对 WebSocket 和 MCP 的基本认识。不必先学 Actor 或 DI。

## 2. 第一阶段：先建立整体认知

读 `README.md`（知其总览有缺口）、`docs/deploy/README.md`、`openspec/specs/engine-runtime/spec.md`、`engine-tool-dispatch/spec.md`。对照 mermaid：客户端 → Gateway → Engine → workspace。

验收：能画出 Model B，并指出 TypeScript workspace 不是生产执行面。

## 3. 第二阶段：优先吃透核心主链路

阅读顺序：

1. `packages/reach-rpc/src/index.ts`（信封）
2. `packages/reach-rpc/src/gateway.ts` 的 `executeRpc` 与 session 状态字段
3. `crates/reach-rpc/src/bin/engine.rs`
4. `runtime/state.rs` → `runtime.rs` 的 `step()` → `execution.rs`
5. `dispatch/dispatcher.rs` → `authorizer.rs` → `canonical.rs`
6. `tools/fs_read.rs` → `workspace.rs` 的 openat/NOFOLLOW 入口

验收：不看文档能说出 duplicate requestId、deadline、grant 缺失各返回什么。

## 4. 第三阶段：拆解关键模块

- process：`docs/deploy/processes.md` → `process.rs` → `tools/process.rs` → `grants.ts`
- MCP：`mcp/tools.ts` → `server.ts`（stdio）→ `http.ts` + `remote-server.ts`（HTTP）
- 部署：`scripts/verify.sh`、`docs/deploy/node-runtime.md`

可延后：OpenWrt 交叉编译、plugin 生成脚本细节、archived OpenSpec changes。

## 5. 第四阶段：理解工程化与配套能力

`scripts/verify.sh`、两端 fixture（`scripts/validate-round1.sh`）、版本号三处来源。注意 connector 必须先 build `reach-rpc`。

## 6. 第五阶段：尝试局部重写 / 仿写

不要一上来重写 Runtime。有价值的仿写：给一个新 `fs.*` 方法走完 Tool + 授权 + 测试；或把 `gateway.ts` 的 session 状态提成纯函数模块做原测试。

## 7. 第六阶段：独立重建最小可用版本

最小切片：loopback Gateway + Engine heartbeat + 一个 `fs.read` + 一个带 grant 的 `fs.write`。process 和 HTTP MCP 是第二切片。

## 8. 推荐阅读顺序与实践顺序

契约 → Runtime 状态机 → Dispatch → Workspace 安全 I/O → Gateway 会话 → MCP 适配 → process。反向从 MCP 工具名读起容易把适配器当成执行器。

## 9. 每阶段产出物与验收标准

每阶段能用自己的话讲一条失败路径（过期 lease、伪造 grant、嵌套 tool.call、未启用的 process workspace），而不是只能讲 happy path。

## 10. 常见误区与避坑建议

- 不要把 Gateway 当执行器，也不要把 MCP 当沙箱。
- 不要用 GoF 清单衡量本仓库；先看端口和状态机是否还完整。
- 不要信任根 README 的环境变量归属和工具列表，以 `docs/deploy/` 与源码为准。
- 不要自动重放写或 `process.run`；先读 revision / 用同一 launchId 查 status。

# 总结与建议

- 优点: 安全模型严谨；Runtime 状态机和传输端口可测；授权与 `tool.call` 规范化在转发前完成；process 默认关闭、固定解释器、session 所有，产品边界清楚；主路径测试厚；10-07 指出的若干正确性洞已经补上。
- 待改进: 文档/OpenSpec 总览滞后于 process 与完整 HTTP 面；process 未入共享契约；`gateway.ts`/`workspace.rs`/`runtime.rs`/`process.rs` 过重；MCP 用继承复用；构建拷贝无契约测试。
- 不要做: 为“设计管理”引入更多模式、插件框架、沙箱、async 重写。
- 建议动手顺序:
  1. P0 文档/spec：心跳变量归属、`shutdown`、OpenSpec 工具列表、plugin process skill。
  2. P1 契约：process DTO + `permission.kind` 进两端共享层与 fixture。
  3. P2 切分：Gateway session 状态、workspace 内部模块、MCP 改为组合。
- 总体评价: 这是一套有设计框架、安全意识强、正在从“文件系统 RPC”长成“文件系统 + 可信进程”的边侧执行器。分数被可维护性和文档总览拖住，不是被主路径正确性拖住。整仓约 **7.7/10**，值得沿现有框架演进，不值得推倒重来。
